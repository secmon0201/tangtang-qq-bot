# 服务守护与恢复记录

Harness 使用自己的 Windows 当前用户计划任务，监督 Harness、Core、SnowLuma 和独立语音进程。它与仓库根目录的旧 NoneBot 看门狗分别运行；新守护不会启动旧 NoneBot，也不会修改旧系统的开关、配置或数据。

守护的依据是保存的服务期望状态和当前开关。过去运行过、安装文件存在或配置项存在，都不能代替“现在应当开启”。显式停止入口先登记关闭意图，再停止进程，因此下一次检查不会撤销操作者的停止选择。

## 状态与文件

`data/supervisor.db` 独立保存守护总开关、各服务的期望状态、检查结果、恢复退避时间和事件。它不使用聊天数据库存储守护状态，不改变模型容量、上下文窗口或保留轮数。数据及日志属于 ignored 运行数据，不进入 Git。

运行模式、`speech_enabled` 和 `extra.core.enabled` 由 `config/settings.json` 保存，控制台修改后写回该 JSON；独立语音开关由 `config/speech.json` 保存，显式语音停止另存 `runtime/speech-runtime/stopped.flag`。这些开关与守护数据库中的服务意图共同决定能否恢复。业务 SQLite 中的群语音开关只约束语音交付，不代替进程开关。

控制台和命令行区分以下状态：

| 状态 | 含义 |
| --- | --- |
| 守护已启用/停用 | 是否允许外部检查执行恢复。停用守护不停止已运行的服务；原有语音后台恢复规则见下文。 |
| 期望开启/关闭 | 操作者或启停入口保存的服务意图。 |
| 进程运行/缺失 | 经过归属核验的自有进程是否存在。 |
| 就绪/连接异常 | 服务的健康或连接状态；进程存在不保证 QQ 登录、Core 连接或语音加载已经完成。 |
| 等待重试 | 最近恢复失败，尚未到下一次允许尝试的时间。 |

进程记录与实际 PID、创建时间、命令或端口不符时，记录错误并保留现场。守护不结束端口占用者，也不根据端口监听就认领其他进程。

## 启停意图

继续使用[运行入口](运行入口.md)里的中文快捷方式和脚本。所有服务操作共用生命周期控制器和文件锁，登记意图及启动/停止在同一受控操作内完成，避免人工操作和定时恢复同时启动两份进程。

| 操作 | 守护行为 |
| --- | --- |
| 启动 Harness/Core/SnowLuma | 先保存对应服务期望开启，再执行启动。失败时仍保留开启意图，守护按退避重试。 |
| 停止 Harness/Core/SnowLuma | 先保存对应服务期望关闭，再停止自有进程。其他独立服务的意图不变。 |
| 重启 Harness | 在生命周期锁内停止并启动；保留其他服务的意图和语音保存开关。 |
| 启动全部 | 按 Core → Harness → SnowLuma 启动；语音沿用已保存的开关。 |
| 关闭全部 | 先关闭全部服务的恢复意图，再按 Harness → Core → SnowLuma 关闭；语音保存开关保留，QQ 保持独立。 |
| 显式停止语音 | 记录关闭意图并保存 `runtime/speech-runtime/stopped.flag`，不被后台语音检查或外部守护重新开启。 |
| 显式启动语音 | 保存开启意图，使用独立语音显式启动入口；配置允许且启动成功后清除先前停止标记。外部恢复不会清除该标记。 |

Core 恢复还要求运行配置中的 `extra.core.enabled` 开启。语音恢复还需要 Harness 期望开启且实际运行、模式为 `live`、Harness 的 `speech_enabled` 开启、`config/speech.json` 的 `enabled` 开启，并且没有 `stopped.flag`。关闭其中任何一项都不会因看门狗而被重新开启。应用正常退出停止其拥有的语音子进程时，保留既有语音选择。

直接在任务管理器里结束一个进程无法可靠表达“以后不要启动”。保存的期望状态仍为开启时，守护将它视为意外退出并尝试恢复。希望保持关闭时，使用对应停止快捷方式或脚本。

## 安装与管理

在 Harness 根目录执行：

```powershell
.\scripts\watchdog.ps1 -Action install
.\scripts\watchdog.ps1 -Action enable
.\scripts\watchdog.ps1 -Action status
```

`install` 只登记计划任务，不启用恢复。`enable` 对尚未保存意图的服务进行盘点，只纳入当前归属核验通过的运行服务，已停止的保持关闭；已保存的意图原样保留，尤其不会覆盖先前的显式关闭。之后通过对应启停入口设置意图，不根据文档中的历史运行状态开启任何功能。

计划任务名称为 `TangtangHarness-Watchdog-<根目录哈希>`，使用当前 Windows 用户，在登录时和每分钟调用一次 Harness 自有虚拟环境的 `pythonw.exe` 执行 `scripts/watchdog_runner.py`。任务直接执行无窗口 Python 入口，不直接调度 PowerShell。检查与后台子进程均使用隐藏窗口；runner 将子检查限时为 45 秒，计划任务限时为 50 秒，额外时间用于结束检查编排及记录失败。

超时或失败写入 `data/supervisor.db` 的检查失败事件及 UTF-8 `logs/watchdog-supervisor-check.log`。超时只终止检查和编排进程，不因此结束已经启动的自有服务；下次检查继续核对实际 PID 和归属，避免重复启动。

```powershell
# 立即进行一次检查；启用守护时可能实际恢复缺失服务
.\scripts\watchdog.ps1 -Action check
# 暂停外部自动恢复，保留当前服务和保存的期望状态
.\scripts\watchdog.ps1 -Action disable
# 重新启用后，以当前保存的意图和开关恢复监督
.\scripts\watchdog.ps1 -Action enable
# 先停用恢复，再移除本 Harness 计划任务；保留运行数据
.\scripts\watchdog.ps1 -Action uninstall
```

`status` 是状态查询，同时显示本 Harness 计划任务是否存在、任务状态和最近触发结果；`check` 使用同一限时 runner，可能执行启动，不把两者当作同一个只读动作。安装和启用是运行操作；首次安装模板不自行登记计划任务或接管服务。已有环境部署时先核对当前服务归属和保存开关。

## 恢复边界

守护只恢复“期望开启、相关开关允许、确认自有进程缺失”的服务。进程仍在、OneBot 或 Core 暂时断开时，只记录连接异常，由已有连接后台任务继续重连，不执行自动杀进程重启。缺少文件、端口冲突、登录失效或语音资源加载失败会记录具体结果，不自动修改配置、登录账号或切换声线。

每次检查最多尝试恢复一个缺失进程，按 Harness → Core → SnowLuma → 语音顺序选择满足条件的服务，保证本轮不累加多个长启动。多项同时退出时会分几轮恢复，因此恢复完整链路可能需要数分钟。

一次失败后的恢复间隔依次为 60、120、300、900 秒，之后保持 900 秒间隔；成功后清除这次失败退避。每项服务独立记录，处于退避的失败服务不会占用本轮启动机会，因此 Core 故障不会一直阻止 SnowLuma 或语音的恢复。生命周期锁忙时本轮跳过，后续计划任务再检查。

Core 和 SnowLuma 复用当前工程既有的进程管理实现和本机安装，不改上游源码、配置或数据库。SnowLuma 启动后仍可能需要操作者手工完成 QQ 登录、二维码、验证码或设备验证。服务恢复成功也不等于模型请求或 QQ 回复链路已经验收成功。

守护启用时，语音进程也由外部守护统一恢复并保存尝试与结果，Harness 内部每 15 秒的语音任务只检查 API 健康，不竞争拉起进程。守护停用时，已保存的语音期望关闭仍会阻止内部恢复；未关闭的语音意图可沿用原有 15 秒后台恢复。希望语音保持停止时，使用显式语音停止入口。启用外部守护后的恢复时间线以 `data/supervisor.db` 为准；停用外部守护期间的原有语音后台恢复不补造为外部守护事件。

## 控制台与事件

本机控制台的“业务与运行 → 看门狗”读取 `GET /api/watchdog`，展示守护开关、各服务的期望和检测状态、最后检查、最近恢复、下一次重试及错误。事件列表保存检测、意图变化、恢复尝试、恢复成功或失败的时间、来源、原因、结果和新 PID。页面按新到旧显示最近 100 条，时间使用北京时间，守护历史不受聊天与模型筛选影响。

例如 Harness 已运行但 Core 退出，会记录 Core 缺失及其恢复结果；Harness 自己退出时，外部计划任务先写恢复记录，Harness 再次启动后即可读取同一历史。重复健康检查不为每分钟都追加“正常”事件，状态变化和实际恢复尝试才形成时间线。事件不包含 QQ 消息正文、凭据或完整模型请求。

Harness 停止时控制台不能打开，可用 `watchdog.ps1 -Action status` 检查。历史记录表示当时的动作和结果；判断当前状态仍需核对实际进程、端口及 `/api/status` 的连接状态。

## 验收

隔离测试应覆盖意外退出恢复、显式停止保持关闭、关闭全部不会被重新拉起、语音多重开关、并发启停、错误归属、端口冲突和独立退避。生产部署还要核对当前用户计划任务的 `pythonw.exe` 入口、实际触发记录、守护数据库事件和 API/控制台；未经实际结束和恢复的服务，不能宣称已经完成该项实机恢复验收。

验证证据放在 ignored 的 `runtime/verification`。公共文档不记录实际账号、群号、个人域名、机器路径或任务哈希。
