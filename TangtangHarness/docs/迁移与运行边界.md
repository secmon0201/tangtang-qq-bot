# 迁移与运行边界

TangtangHarness 直接接入 SnowLuma 的 OneBot v11，使用自己的 Python 环境、配置、数据库、入口、日志、工具和前端。外部 NoneBot 目录保留，不作为新系统的模块或运行依赖。已有算法、资源和行为可以移植到新目录，框架绑定需在新目录替换。

## 三个运行阶段

| 阶段 | 入站与业务 | 对外行为 |
| --- | --- | --- |
| 离线 | 合成事件与消息回放、请求预览、工具行为验证 | 不调用付费模型，不发 QQ |
| observe | 通过独立 8090 endpoint 捕获真实事件，写入新库 | 不启动聊天，不调用模型，不发送 QQ，不连接共享 Core 执行业务 |
| live 测试 | 只接单独指定的测试范围与专用呼叫词 | 仅已明确启用的新功能执行；旧受管群与私聊自动回复不并行接管 |

observe 捕获记录可以用于检查会话、路由和上下文，不应在切成 live 时自动补做历史工作。导入的旧 pending、语音、续聊、主动发言和发送队列都只作历史，不重启补发。后台整理的启用是独立设置；上线不默认重新消费旧工作队列。

生产切换需要单独运维窗口；当前工作区已经完成一次切换，Harness 作为唯一日常接单者运行，旧 NoneBot 保留回切入口。开发、安装、预览和 observe 不应停止旧机器人或更改旧开关。

## SnowLuma 并行连接

保留旧 `127.0.0.1:8080` 的反向 WS，新增 Harness 独立 `127.0.0.1:8090` endpoint。SnowLuma 发行版静态实现支持多网络适配器；双连接需要实际联调验证。

只允许对共享 SnowLuma 做明确的新增 endpoint 操作。不要用旧 `configure_snowluma.ps1` 来配置新应用，不改旧源码与业务配置，不自动增补 endpoint。

旧 `start_snowluma.ps1` 在检查进程前会调用旧配置器，而旧配置器会重写 OneBot 配置、只保留旧连接。因此旧全栈启动或传输恢复后，新 endpoint 可能丢失。请使用新目录提供的显式检查/增补工具或在 WebUI 手动补回；补回只更新 Harness 网络项并保留已有项。不要新增常驻自愈进程或改变旧启动脚本。

新 Harness 的启停只管理自己的进程，不能启停共享 SnowLuma、QQ 或旧 Core。QQ 登录、扫码、设备验证继续由用户操作。

同账号同群相同触发词会让两个系统同时回复。新聊天 live 首先使用非旧受管测试群和专用词；私聊旧框架本身自动回复，不能依靠专用词实现双系统互斥。

## 数据迁移

读取旧 SQLite 时用来源只读连接进行在线 backup，把一致的单库快照写到新目录。不要调用旧 Database、PersonaStore 或全局 runtime constructors；它们可能初始化和修改数据库。不要直接复制仍在写入的 `.db` 文件而遗漏 WAL，也不要将活跃库作为 immutable 来源读取。

每个快照记录来源、完成时间和迁移进度。多个库顺序快照是各库自己的时间点，不是全局原子快照。

- 原始消息与历史执行记录按来源主键和平台 message_id 去重增量。
- 可变开关、群成员、关系状态、记忆 revision 等按最终来源版本同步，不能只用最大 id 增量。
- 新试运行记录保留独立来源，不被旧快照覆盖。
- 只有明确的成功交付状态与平台 message_id 才表示已经发送；存在模型回复文本不代表用户收到。
- 历史请求和未完成队列保留作记录，不变为 live 的待执行任务。
- 导入完成时间写入新库 `import_cutoff`。榜单定时推送、整点槽与缘分集体事件从此后开始；旧活动小游戏在新运行库标为取消，原始状态仍保存在来源快照中。

再次正式接管或回切时，由独立运维流程停止当前接单者和对应监督，等待当前任务确定结束，再按需要做最终快照与增量同步后启用新的唯一发送者。旧文件和旧数据库不删除。本次切换已完成该流程；此前的并行快照只用于迁移验证。

## 游戏与语音

游戏只保留明确 `#nte`、`#ww` 命令透传，解析、帮助、渲染和排行由上游拥有。新目录自建 Core 协议 adapter，保持 Core/NTEUID/鸣潮源码与 `GsData.db` 只读边界；不能移入依赖 NoneBot 的旧 connector。

Core 的 URL `/ws/{连接标识}` 与消息中的 `bot_id`（平台）、`bot_self_id`（QQ 身份）分别存在。新连接使用独立 route identity，不能覆写旧 Core 连接。更换 route identity 会改变上游 session，账号、订阅、回执和消息发送必须经过协议夹具验证。真实游戏测试与生产运行均使用唯一命令转发者，不双重执行同一命令。

语音首期关闭。语音迁移使用独立服务端口和自己的缓存、队列、readiness、监督状态。旧 GPT-SoVITS API 的切权重接口会改变共享模型；旧服务内的进程级队列不能协调另一个客户端。若选择共享固定声线，只允许调用既有合成接口，不切权重、不启停旧服务，并先验证服务端并发与旧回复耗时。不能将旧 SpeechSupervisor 直接作为新监督器。

新目录提供默认关闭的 [独立语音运行器](独立语音运行时.md) 与 `start_speech.ps1`、`stop_speech.ps1`。它使用 `9890`、自有 YAML 和源码副本，缓存写入新目录；源码副本用于隔离 GPT-SoVITS 的源码侧词典缓存写入。进程存活、API 就绪与真实合成分别验收。

上游依赖、头像和截图缓存不得被新清理任务删除。新运行清理只覆盖新目录自有缓存，历史快照和备份不自动删除。

启动时及每六小时清理新目录的 `runtime/reports`、`runtime/screenshots`、`runtime/speech` 和 `reports`，默认保留 24 小时，可通过 `extra.retention_hours` 调整。`runtime/avatars` 按用户仅保留当前版本，不按图卡期限删除当前头像；`data` 中的媒体、历史快照和备份不参与清理。
